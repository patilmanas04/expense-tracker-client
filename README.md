# Folio · expense dashboard

Next.js 16 frontend for the FastAPI SMS expense tracker in `../expense-tracker-server`. Built mobile-first for iPhone, with a sidebar layout on desktop.

## Run

```bash
npm install
cp .env.example .env.local   # optional, defaults to http://127.0.0.1:8000
npm run dev                  # http://localhost:3000
```

Start the backend first (`uv run uvicorn main:app --port 8000` in the server folder). Next.js proxies `/api/v1/*` to `BACKEND_URL`, so the browser only talks to this origin and the backend's session cookie stays first-party. Google sign-in, the webhook and the iPhone Shortcut are configured in the backend README.

**Production:** rewrites are resolved at build time, so set `BACKEND_URL` **before** `npm run build`, then `npm start`. For iPhone access use a stable HTTPS domain and point the backend's `FRONTEND_URL` / `GOOGLE_REDIRECT_URI` at it. Previewing `next dev` from a phone over your LAN needs that address in `allowedDevOrigins` in `next.config.ts`, and Google sign-in won't work on a bare LAN IP.

**Balance left** (Settings → Bank balance) is the bank balance you saved there, minus debits and plus credits recorded since you saved it. It is **HDFC and ICICI together** (one number for both banks). The backend computes it (`/api/v1/balance`), so it matches what the SMS webhook returns. Credit-card spends count when the card bill is paid. See the backend README. **Read at** (under the amount when saving) says when you read the balance: **Now** (the default; the app sends no time and the server uses its own), or Today, Yesterday or one of the 5 days before that with a time, taken as IST and sent as `as_of`, so payments between reading the bank app and saving in Folio are counted. The app keeps it within the last 7 days and not in the future ("Pick a time in the last 7 days.", "That time hasn't come yet."); the server only refuses future times. **How it's worked out** (`/settings/balance`, a page of its own like the spending limits page) explains the number from `GET /api/v1/balance/breakdown`: the starting balance and when it was read, money in and money out since then, then **Not counted**, grouped by reason in the server's order (unreadable SMS, another currency, possible duplicates held out, cash, credit-card spends) with each group's count and signed total (unreadable and other-currency groups show only a count, since their amounts can't be added up), each tapping open to its transactions (newest first, 50 at a time with **Show 50 more**), and **Counted**, newest first with the effect of each and the balance after it, rendered 50 at a time as you scroll. Tap any row to open its sheet. The page refetches whenever the balance or transactions change (the 5-second poll), keeping the old figures on screen meanwhile; with no balance saved it links back to Settings. The transaction sheet labels the SMS's "Avl Bal" by whose figure it is, as the server decides (`balance_kind`): **Bank balance in SMS** (one account's balance, including a card bill paid from the bank) or **Card limit left in SMS** (a credit card's limit left); neither is Balance left. **Alert me below** (in the saved balance, under How it's worked out; hidden with no balance saved, while updating it, or when settings couldn't load) works like **Payments over**: turning it on asks for an amount in whole rupees (1 to 10,00,00,000; `₹`, commas and spaces are fine; Off by default) and **Save** stores it, the row then shows "Below ₹10,000" with **Change**, and turning the switch off saves Off at once. You get one notification (in the bell only, never emailed) when a payment, an SMS or one added by hand, takes Balance left from at or above that amount to below it; not again until a later payment crosses it again after the balance rose back. Saving a balance, changing the amount, edits and deletes never alert. The server decides (`PUT /api/v1/settings` with `alerts.low_balance`); removing the balance keeps the saved amount, the row just hides.

The **bell** on Home opens the notifications drawer. Spend-limit notifications (`spend_limit`, coral gauge) and near-limit warnings (`spend_warning`, amber gauge, "80% of your monthly Food & Dining limit used") open the spending limits page, a "Possible duplicate" notification opens Activity on *Needs review*, a low-balance notification (`low_balance`, red wallet, "Balance low: ₹9,200.00 left") opens How it's worked out (`/settings/balance`), and recurring notifications (`recurring_new`, violet repeat, "New recurring payment: Netflix"; `recurring_price`, amber trend, "Netflix went up: ₹649") open Recurring (`/report/recurring`). A pinned row ("3 items need review": SMS Folio couldn't read, and possible duplicates) opens the same list. Some notifications carry buttons (for example, to confirm a suggestion): tapping the row's text only marks it read, a button runs its action and the result (such as "Marked as done") replaces the buttons after the next refresh; if the action fails, its reason shows in the row. A notification without a link and without buttons only marks itself read. Links of the form `/activity?kind=review`, `/activity?tag=goa` and `/activity?txn=<id>` open Activity with that filter (clearing the others), or with that transaction's sheet open (`lib/links.ts`); Activity itself never reads URL parameters. Any other link opens as a page. Each kind has its own icon and colour (`KIND_STYLES` in `components/notification-drawer.tsx`). The red dot means unread notifications. **Clear** (next to ✕) clears them all, and swiping one left deletes it; either way the alert still counts as sent, so it isn't repeated. Tap any transaction for the detail sheet with the original SMS. A **possible duplicate** (the server found an earlier transaction that looks like the same payment: same reference number, same amount and merchant within minutes, or a hand entry matching a bank SMS) is greyed in lists with a *Possible duplicate* chip and counts in no total (Spent, Income, Balance left, limits) until you decide. Its sheet links to the earlier transaction and offers **Delete duplicate** (the usual delete, with Undo) and **Not a duplicate** (it counts again and is never flagged again). Deleting the earlier one instead makes the flagged one count again within one poll. **Delete** any transaction by swiping its row left (iOS style: a long swipe deletes at once) or with the bin next to Edit in its sheet; **Undo** shows for 5 seconds before the delete reaches the server (leaving the app sends it at once). Spending limits swipe left to delete the same way (`components/swipe-to-delete.tsx`). **Edit** (top left, iOS style) changes its amount, name, category, type or date; a new category is remembered for that merchant, so its next SMS gets it too. Typing a new name for a payment that has one shows a box under the name, unticked: "Also rename the N other payments named “SWIGGY” (any case), and future ones" (N counts the other loaded payments with that name, any case and spacing, that aren't already the new name; with none it reads "Also rename future payments named …"). Saving with it ticked merges the name on the server (`POST /api/v1/merchant-names`, which renames this payment too), then sends any other changed field, then reloads every transaction; "Saving…" stays until the reload is done. Unticked, only this payment changes. A payment filed by one of your category rules says so under Category: "Set by one of your category rules. Future payments like this follow it." with a **Names and rules** link (which also closes the sheet); changing its category in Edit changes that payment only. **Add a note** (below the details) keeps your own note on any transaction, such as where it was or what it was for: it shows under the row in lists, Activity search finds it, and Edit next to it changes or removes it. Write `#goa` (any language; letters, digits, `_`, `-`; up to 30 characters with at least one letter, after a space or punctuation) in a note to **tag** it: tags show as chips under the row and in the sheet, tapping one opens Activity filtered to it, and while you type `#` and the start of a tag the note editor suggests existing tags (up to 5, most used first; tapping one completes it). The rule is in `lib/tags.ts`. On phones, swipe either sheet down by its top bar to close it: a short drag springs back, a longer drag or a quick flick closes it (`components/sheet-drag.ts`). Category cards and donut legends open Activity pre-filtered.

**Alerts** (Settings → Alerts, below Bank balance) has two switches; both notify in the bell, once per payment. **Payments over**: turning it on asks for an amount in whole rupees (1 to 1,00,00,000; `₹`, commas and spaces are fine) and **Save** stores it; any later payment *over* that amount (not equal to it) gets a "Large payment" notification. The row then shows "Over ₹5,000" with **Change**; turning the switch off saves Off at once. **Unusual for the merchant** (on by default) flags a payment of ₹500 or more that's at least 3× the median of your payments to that merchant over the last 180 days (it needs at least 3 earlier payments there). Only counted rupee debits read from SMS or added by hand are checked; held-out duplicates are checked if you mark them *Not a duplicate*. The server decides everything (`GET` / `PUT /api/v1/settings`); settings load with everything else, aren't polled, and when they couldn't be loaded the section says so and **Sync** retries. A payment alert (`payment_alert`, red badge icon) opens that payment's sheet over Activity (`/activity?txn=<id>`).

**Spending limits** (`/settings/limits`, from Settings → Manage spending limits) is a page of its own: a back button on top and no tab bar (pages below a tab hide it, `components/app-shell.tsx`). It lists the overall limit, each category's and each merchant's with live meters; **+** adds one (weekly and/or monthly, for all spending, a category or a merchant), **Edit** changes it, and swiping left deletes it. Back goes where you came from, or to Settings when the page was opened directly. **Warn me at** (at the top, Off or 50% to 95% in steps of 5, 80% by default) is saved as soon as it's picked (`limits.warn_percent` in `GET` / `PUT /api/v1/settings`; the server's message shows under it if the save fails): the server sends one warning notification per limit and period when spending reaches that level but is still under the limit, then the usual one when the limit is reached. Under each meter with a limit, a line says what's left: "₹850 left · about ₹85 a day for 10 days" (days count from today to the period's last day, both included; "today is the last day" on that day), "Nothing left" or "₹120 over" (`leftToSpend` in `lib/analytics.ts`; whole rupees, left and per day rounded down, over rounded up). The bar turns amber at the warning level (at 80% when warnings are Off) and red at the limit; the same meters in Settings follow it.

**Names and rules** (`/settings/rules`, from Settings → Names and rules) is built like the spending limits page (back button, no tab bar, **+**). **Merged names** lists each merge ("SWIGGY → Swiggy", newest first); merges are made from a payment's Edit (above), and swiping one left stops renaming future payments (names already changed stay). **Category rules** lists one line per rule ("SMS has rahul@okaxis · money out · ₹15,000 or more → Bills & Utilities", newest first; the newest rule that matches wins); tap one to edit it, swipe it left to delete it (categories it set stay), **+** adds one. The rule sheet has *Name has* and *SMS has* (whole words, in order, any case), *Money* (Either / Out / In), *At least* (₹) and *Category*; at least one of the words or the amount is needed. **Check past payments** asks the server how many past payments the rule would change (`POST /api/v1/rules/preview`, which writes nothing) and shows up to 5 of them; the box under the answer, "Also change these N payments", is unticked by default and only counts while the form still holds the values that were checked. Without it, the rule only files future SMS and payments you add. Server messages show under the form. The server does all the matching; the app never re-implements it.

**Merchant limits** (the sheet's *Merchant* switch; **+** opens on it once every category has a limit) cap one merchant, such as Swiggy. Pick a merchant you've paid before, or type one: while you type, the sheet suggests known merchants containing the text (any case, up to 8, most payments first; arrow keys and Enter pick one, Escape closes the list). A typed merchant the server doesn't know yet is saved as a known merchant, spelled as typed, and the sheet asks for its category, which merchant memory then gives its future SMS; a merchant picked from the list keeps its category. Typing a name that already has a limit loads its amounts, and saving updates it; **Edit** changes only the amounts. A limit counts every payment whose merchant name contains its name as the **same whole words with the same upper and lower case**: a "Swiggy" limit counts "Swiggy" and "Swiggy Ltd", but not "SWIGGY" (as an SMS read by the AI may store it), "swiggy" or "Swiggyone". So you can see what's included, each merchant limit lists the names it counts ("Counts: Swiggy, Swiggy Ltd", or "Counts: no payments yet"), on the page and in the sheet before you save. The server does all the matching (`/api/v1/limits/merchants/*`); the app never re-implements it. Merchant limits count toward "N limits set" on Settings.

**Tab bar** (phones): tap a tab or slide along the bar and let go. It navigates on release, for taps and slides alike, because browsers often send no click once a finger has moved; the trailing click, if any, is swallowed. Keyboard, screen-reader and Cmd-clicks go through the links (`components/nav.tsx`).

## Sign-in gate

`proxy.ts` runs before every page. Without a signed-in session cookie (`folio_session` from the backend, with a `user_id`), it redirects to `/login` at the server, so the dashboard is never sent. With one, `/login` redirects to `/`. This only *reads* the cookie, so it can't tell a forged or stale cookie from a real one; the backend still verifies the signature on every API call. If it answers 401, the app goes to `/login?expired=1`, which the proxy never bounces back, so there's no redirect loop. The dashboard routes live in `app/(dashboard)/` with their own layout, so `/login` loads no dashboard code or data.

## Theme

Settings → Appearance offers System, Light and Dark, saved in this browser (`localStorage`, key `folio-theme`). A tiny inline script in `app/layout.tsx` puts `data-theme` on `<html>` before the first paint, so a dark-mode user never sees a light flash; `components/theme.tsx` keeps it in sync with the choice, the OS setting and other tabs. Every colour is a token in `app/globals.css` (`@theme` for light, `:root[data-theme="dark"]` for dark), so components never hard-code colours.

## How numbers are computed

- All transactions are fetched once (200 per request). After that, the app **polls every 5 seconds** while it's visible. Each poll asks only for rows added or changed since the newest change it has (`updated_after`, with a 15 s overlap de-duplicated by id) plus the balance, so edits and categories filled in later by the server show up live, and an idle poll is a few hundred bytes. Hidden tabs and a locked phone don't poll. Coming back after a minute does a full refresh. The "Couldn't refresh" banner appears only after 3 failed polls in a row. Spending limits load at startup alongside everything else (so Settings opens with them filled in) and refresh whenever a new SMS arrives; pay periods load and refresh with them. After a merged name or a rule applied to past payments changes rows, the app reloads every transaction (`refresh()`), because one poll can't carry more than 200 changed rows. A reload asked for while a poll is in flight runs right after it, never dropped, and `await refresh()` resolves only once the reload is done.
- Money is summed in paise (integers). Dates are grouped in India Standard Time.
- SMS the backend couldn't parse (`is_parsed = false`) and possible duplicates you haven't decided on (`duplicate_of` set) are listed under *Needs review* and never counted in totals (`isHeldOut()` / `needsReview()` in `lib/analytics.ts`). Possible duplicates also stay in the Expenses / Income lists, greyed; the day header's Spent leaves them out.
- **Only real spending counts.** Two category sets in `lib/categories.ts` decide it (`counts()` and `isInvested()` in `lib/analytics.ts`):
  - `NOT_COUNTED` (**Credit Card Payment**, **Self Transfer**): paying a card bill and moving money between your own accounts are neither spending nor income. The card spends themselves already counted when you swiped the card.
  - `INVESTED` (**Investments & Finance**): money put into investments and deposits (SIPs, mutual funds, FDs, PPF) isn't Spent; Home shows it on its own **Invested** card (only in months that have some) and the Report's Expenses view adds "Invested: ₹… · not in expenses" under its stats. Money coming back from investments counts as nothing, not Income.
  - Everything else counts: debits are Spent, credits are Income. That includes **Cash Withdrawal**, **Transfer** (money to or from other people) and transactions with no category.
  - **Net flow** = Income − Spent − Invested.
  - The sets are copies of `NOT_COUNTED` / `INVESTED` in the backend's `spending.py`, which spending limits use; the backend's `tests/test_spending.py` reads this file and fails if they differ (and if the category list here isn't the backend's, in order). Change both together. These categories still show in Activity (filtering by one shows Spent ₹0), and they can't have a spending limit.
- "vs last month" compares the same days of the previous month, or the same number of days into the previous pay period, while a month is in progress.
- **Salary counts toward the month it pays for.** With **Month starts on payday** off (the default), a credit in **Salary** received on the 16th or later counts toward the next month (the month holding most of the month after payday): salary paid on 31 Oct is November's income, from the 1st. Salary paid on the 15th or earlier (say, late on 2 Nov) counts in its own month. This applies to Income, Net flow, Report, the cash-flow chart and insights; the transaction still shows on its real date in Activity, tagged "Counts in Nov", and Balance left and spending limits are unaffected. Other money in uses **Income** and counts on the day it arrives. If your employer's SMS doesn't say "salary", set it to Salary once with Edit; merchant memory does the rest.
- **Pay periods** (Settings → Appearance → **Month starts on payday**, off by default). With it on, a month starts on the day a Salary credit arrives and runs to the day before the next one. It's named by the 16th rule above (salary on 31 Oct opens "Nov"; a second Salary credit with the same name, such as a bonus, starts nothing), and it ends by the 15th of the month after its name at the latest. Days outside every pay period (before the first salary, or after a period's latest end when no salary came) count in their calendar month, cut to those days. A late salary just extends the current month; nothing is predicted. Labels read "Nov · 31 Oct – today" for the current month and "Oct · 30 Sept – 30 Oct" for past ones (with the year when it isn't this year's); the current month's last day is the expected one (the day before the same date next month, never before today), used for the calendar and days left. Home, Report (every card, including daily bars over the period's own days and pace), Activity's month filter and calendar, and monthly spending limits and their alerts follow it, and the "Counts in Nov" tag goes away; weekly limits (Monday–Sunday) and Recurring's monthly total don't. Periods come from the server (`GET /api/v1/periods`, worked out from your Salary credits on every read), so editing, recategorising or deleting a Salary credit moves the boundaries at once. With the setting on and no Salary credit yet, months stay 1st–end and the setting says so. The rules are in `lib/periods.ts` (`monthCalendar`).
- **Habits** (Report, Expenses view, INR only; hidden when it has nothing to show), from the loaded transactions (`frequentSmallSpends()` / `biggestPayments()` in `lib/analytics.ts`): *Frequent small spends* lists merchants with at least 8 counted debits under ₹500 each this month, grouped by the Top merchants key (name trimmed, any case), up to 5, most payments first, with the count and their total. *Biggest payments* lists the month's three largest counted debits by full amount (newest first on a tie). "This month" means the month a payment counts in, like the rest of the Report.
- Each category has a fixed colour (`lib/categories.ts`), so it doesn't change colour from month to month. The palette was checked for colour-blind separation.

- `lib/analytics.ts`: all aggregations (pure functions)
- `lib/format.ts`: IST dates and `en-IN` currency formatting
- `lib/tags.ts`: the `#tag` rule (shared with the backend's goal tags later), tag counts and note-editor suggestions; no imports, so Node can test it

- `lib/csv-format.ts`: CSV quoting and the formula guard, amounts from paise, and the export's file name; no imports, so Node can test it
- `lib/trend.ts`: the Spending trend's average, highest and so-far maths; no runtime imports, so Node can test it
- `lib/calendar.ts`: Activity's calendar cells (Monday-first, for a month or any first…last span) and shade steps; no imports
- `lib/periods.ts`: pay periods ("Month starts on payday") as a `MonthCalendar` (which month a day is in, each month's first and last day, the day index) and the open period's expected last day; no runtime imports, so Node can test it
- `components/calendar-grid.tsx`: Activity's calendar
- `components/trend-card.tsx`: Report's Spending trend card (its own file so Home, which imports `insight-cards.tsx`, doesn't load Recharts)
- `lib/csv.ts`: the export's columns and one row per transaction (`transactionsCsv`)
- `lib/save-file.ts`: hands a file to the share sheet on touch devices, or downloads it
- `components/more-filters-sheet.tsx`: Activity's More filters sheet (amount range)
